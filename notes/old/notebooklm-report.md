Technical Integration Report: Wrapping Vortex SimX as a gem5 SimObject

1. **Project Overview and Objectives**

This report details the architectural integration of the Vortex SimX cycle-level simulator into the gem5 modular simulation infrastructure. The primary objective is to encapsulate Vortex—a full-stack, open-source RISC-V GPGPU—within gem5’s object-oriented framework to enable high-fidelity, timing-accurate full-system simulation.

By bridging these two entities, we combine Vortex’s specialized SIMT (Single Instruction Multiple-Thread) execution model with gem5’s sophisticated memory hierarchies (Classic and Ruby) and interconnect models. This integration allows architects to move beyond simple functional verification, enabling deep performance-bottleneck analysis and design-space exploration of GPGPU workloads within a comprehensive system-on-chip (SoC) environment.

2. **The gem5 SimObject Architectural Framework**

As a standard requirement for all gem5 components, the Vortex wrapper must implement a dual-class structure. This design bifurcates the configuration and initialization logic from the performance-critical simulation engine, allowing the GPGPU core to be treated as a composable hardware component.

Feature	Python Class	C++ Class
Primary Role	Initialization and Configuration	State and Simulation Logic
Responsibilities	Defines SimObject parameters (e.g., core count, clock); specifies port connectivity via configuration scripts.	Implements the cycle-by-cycle logic; maintains architectural state; manages hardware handshake protocols.
Base Class	SimObject (Python)	SimObject (C++)
Execution Context	Interpreted at startup for system setup and parameter passing.	Compiled for high-speed, performance-critical simulation; executes the Tick event logic.

This object-oriented paradigm ensures that the Vortex Accelerator Functional Unit (AFU) can be instantiated alongside standard CPUs and connected to gem5's Ruby-based cache coherence protocols, enabling cross-silo performance analysis.

3. **Wrapping the Vortex SimX Core**

Encapsulating the Vortex SimX core within the gem5 SimObject C++ base class requires a meticulous mapping of internal hardware registers to the wrapper's state. The integration utilizes the "Elastic Pipeline" design pattern found in Vortex, which relies on simple handshake protocols to facilitate modularity.

Central to this "glue" logic is the Tag System. Every request in the pipeline is assigned a tag consisting of the Program Counter (PC) and Wavefront ID (wID). These tags are critical for the gem5 wrapper to track instruction life cycles across discrete Tick events and memory port responses, ensuring that state is correctly maintained even during long-latency memory stalls.

The wrapper manages the following microarchitectural components:

* Wavefront Scheduler: Coordinates the selection of wavefronts based on active, stalled, and barrier masks to drive the instruction fetch stage.
* IPDOM (Immediate Post-Dominator) Stack: Essential for managing control flow divergence by tracking thread masks during branch operations.
* Banked GPRs: Handles parallel register access for multiple threads within a wavefront.
* Texture Units: Fixed-function units managed via Control Status Registers (CSRs) for accelerated graphics sampling.

4. **Memory System Integration via gem5 Ports**

Communication between the Vortex core and the gem5 memory hierarchy is mediated through the gem5 Port interface. To achieve high accuracy, the integration operates primarily in Timing mode, which models detailed message interactions and asynchronous responses.

High-Bandwidth Cache and Port Mapping

The integration must account for Vortex's High-Bandwidth, Non-Blocking (NBHB) cache architecture. Unlike standard CPU caches, the Vortex data cache utilizes Virtual Multi-porting and MSHRs (Miss Status Holding Registers) to handle thousands of outstanding misses. The gem5 wrapper maps these internal requests to Port messages as follows:

* Instruction Fetches: The Wavefront Scheduler issues PC + wID tagged requests to the gem5 Instruction Port.
* Data Coalescing: The Load-Store Unit (LSU) and the data cache bank selector coalesce parallel thread requests mapping to the same cache line before issuing messages to gem5 ports, maximizing data block utilization.
* Texture Fetches: The Texture Unit includes a De-duplication unit that filters repeated memory accesses across threads. The gem5 port interface subsequently handles "batches of unique addresses" generated by the Address Generation stage, ensuring efficient memory utilization for graphics workloads.

Vortex data and instruction transfers are seamlessly mapped to either the Classic Memory System for rapid prototyping or the Ruby Memory System for detailed cache coherence and interconnect modeling via the Garnet network.

5. **Simulation Synchronization and Determinism**

Synchronizing Vortex’s cycle-level execution with gem5’s event-driven engine is critical for maintaining simulation determinism. Discrete gem5 events trigger SimX cycle evaluation, ensuring the GPGPU state progresses in lockstep with the system clock.

While gem5’s O3 and InOrder models often utilize an "Execute-in-Execute" philosophy, the integration must reconcile this with Vortex's in-order 5-stage pipeline. To ensure determinism, all architectural state changes—such as register writes and memory commits—are restricted to the Vortex "Commit" stage. Even if gem5's system-level models process a request earlier, the integrated SimObject ensures instruction effects only manifest at the cycle-accurate commit point, preventing non-deterministic state leakage.

6. **SIMT Component Functional Integration**

The functional preservation of GPGPU-specific features is achieved by mapping the Vortex RISC-V ISA extensions directly to the wrapper's internal logic. The following six new instructions are integrated as SIMT primitives:

* Wavefront and Thread Control (wspawn, tmc): The wrapper uses wspawn to activate wavefronts at a specific PC and tmc (Thread Mask Control) to manage the activation of individual threads within a wavefront via CSRs.
* Control Divergence Handling (split, join): When the split instruction is encountered, the hardware pushes the current thread mask and the branch predication results for all threads onto the IPDOM stack. The join instruction pops the stack to facilitate reconvergence.
* Synchronization and Texturing (bar, tex): The bar instruction manages wavefront-level barriers (both local and global) via the barrier control module. The tex instruction triggers the texture unit's address generation and de-duplication logic to perform point or bilinear sampling.
* Banked GPR Access: The wrapper handles parallel thread access within a wavefront, simulating the high-bandwidth register file interactions required by the SIMT model.

7. **Conclusion: Value of the Integrated Environment**

Integrating Vortex SimX into the gem5 environment provides an authoritative tool for the computer architecture research community. By leveraging the OPAE Driver and CCI-P protocol abstractions within gem5, researchers can evaluate the full software stack—from OpenCL/OpenGL applications to the hardware RTL—in a unified, deterministic framework.

The synergy of this integrated environment yields three critical advantages:

1. Full-Stack Co-Design: Researchers can evaluate how RISC-V ISA extensions like split/join and tex interact with full-system services, including the OPAE-based host-to-accelerator communication.
2. Detailed Heterogeneous Modeling: The integration exposes Vortex's internal memory requests to gem5’s Ruby-based cache coherence protocols, enabling the analysis of performance bottlenecks in complex multi-core/multi-cluster configurations.
3. Extensive Design-Space Exploration: The environment facilitates the study of advanced architectures that exceed the capacity of physical FPGA prototyping, such as HBM-based systems or 32-core clusters operating at 200 MHz, providing a scalable path toward ASIC-level development.
